# Plain login wins; cookie paste stays as backup

Plain login, where EdgeLoop posts the user's username and password to the site's own form, is the better main route for Hypnotube and Rule34Video. The copy-paste cookie box should stay as its fallback, not compete with it. As of 22 November 2026 both login forms are short two-request flows with no captcha. Hypnotube posts two fields and has no CSRF token. Rule34Video's standard KVS form needs one token scraped from the page and replies in JSON. What decides the choice is how long a session lasts, not how sign-in works. Hypnotube gives every session cookie a fixed three-day lifetime and has no "remember me", so any route that doesn't keep the password makes the user sign in again every few days. A stored password lets EdgeLoop renew the session without asking, as `IwaraApi` already does for Iwara. That has a real cost. EdgeLoop would hold a reusable password, and a scripted login stops working without warning the day either site turns on a login captcha, which both already use on sign-up. So captcha detection and a working cookie fallback have to ship with it. An embedded WebView2 sign-in window is the right answer if a captcha or bot challenge appears, but it adds a runtime dependency and a second copy of the session on disk to solve a problem that doesn't exist yet. Reading cookies from Firefox takes no effort for this user and is already half in place through yt-dlp's `--cookies-from-browser`. But it works only with Firefox (Chrome and Edge have blocked this since 2024) and it behaves like credential-stealing malware, so it belongs as an extra the user turns on. Separately, EdgeLoop currently passes the Iwara password to yt-dlp on its command line in plain text. That is the cheapest and most urgent fix and should come first.

## Two short forms with no captcha make plain login workable today

Hypnotube's login is about as simple as a web login can be. The page at `https://hypnotube.com/login` holds a plain form that posts back to the same URL with two fields, **`ahd_username` and `ahd_password`. It has no hidden inputs, CSRF token, nonce, captcha or remember-me box**, and the site's scripts have no AJAX login handler ([Hypnotube login](https://hypnotube.com/login)). It asks for a username, not an email address. The site runs Mechbunny's tube script on plain nginx, with no Cloudflare or DDoS-Guard in front ([Hypnotube login](https://hypnotube.com/login)). JDownloader's Hypnotube plugin logs in exactly this way: it loads the page, fills the two fields and submits, and it counts a reply containing `/logout"` as signed in ([JDownloader HypnotubeCom.java](https://github.com/mirror/jdownloader/blob/master/src/jd/plugins/hoster/HypnotubeCom.java)). That code is from 2024 or earlier, and the same field names are still live in November 2026, so the form looks stable.

Rule34Video runs the commercial KVS (Kernel Video Sharing) engine and uses its standard AJAX login: a POST to `/login/` carrying `username` (labelled "E-mail or username"), `pass`, `remember_me=1` (ticked by default), `action=login`, `email_link` and `redirect_to`, plus **a hidden `remember_me_csrf_token`, a 64-character value that changes on every page load** ([Rule34Video login](https://rule34video.com/login/)). The KVS script adds `mode=async&format=json`. The reply is JSON whose `status` is `success` or `failure`, with an `errors[]` list that names the failing field ([kvs.min.js](https://rule34video.com/static/js/kvs.min.js?v=3dbf75d2e5)). An app login is therefore one GET to collect the session cookie and token, then one POST using the same cookies. The Kodi add-on Cumination posts the same KVS fields to other KVS sites in code updated on 20 October 2026, but without the CSRF field this site adds ([Cumination theyarehuge.py](https://github.com/dobbelina/repository.dobbelina/blob/master/plugin.video.cumination/resources/lib/sites/theyarehuge.py)). Rule34Video sits behind DDoS-Guard, but on 22 November it served full pages to a plain HTTP client without any JavaScript challenge. It also offers a cheap sign-in check: `?mode=async&format=json&action=js_user_status` returns `{"id":0}` for a visitor and a positive id for a member ([js_user_status](https://rule34video.com/?mode=async&format=json&action=js_user_status); [custom.min.js](https://rule34video.com/static/js/custom.min.js?v=0046d754f0)).

Neither site offers an API, OAuth or app passwords. That leaves three options: the site's own form, an embedded browser, or cookies borrowed from a browser ([Hypnotube login](https://hypnotube.com/login); [Rule34Video login](https://rule34video.com/login/)). Whichever route EdgeLoop takes, yt-dlp can't log in for it. Its Rule34Video extractor has no login code, and it has no Hypnotube extractor at all ([yt-dlp rule34video.py](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/rule34video.py)). So every route ends the same way: a set of session cookies that EdgeLoop sends from its own `HttpClient` and hands to yt-dlp through the temporary Netscape cookie file it already writes ([YtDlpService.cs](../EdgeLoop/Classes/YtDlpService.cs)). Because every route ends there, they can be built as layers instead of a choice of one.

## Hypnotube's three-day cookie decides the contest, not the login form

Hypnotube sets `PHPSESSID` with a fixed **`Max-Age` of 259,200 seconds, which is three days**. It does this even for visitors who aren't signed in, and it offers no remember-me option ([Hypnotube login](https://hypnotube.com/login)). Rule34Video's `PHPSESSID` lasts only as long as the browser session. KVS keeps members signed in across restarts with a separate `kt_member` cookie, which both JDownloader and Cumination treat as the real proof of login ([JDownloader KernelVideoSharingComV2.java](https://github.com/mirror/jdownloader/blob/master/src/jd/plugins/hoster/KernelVideoSharingComV2.java); [Cumination theyarehuge.py](https://github.com/dobbelina/repository.dobbelina/blob/master/plugin.video.cumination/resources/lib/sites/theyarehuge.py)). Both sites run on PHP, which by default discards a session's data on the server after **24 minutes without use**, unless the site raises that limit ([PHP manual: session configuration](https://www.php.net/manual/en/session.configuration.php)). The three-day figure is only the limit the browser enforces. EdgeLoop's temporary cookie file writes a far-future expiry for every cookie anyway ([YtDlpService.cs](../EdgeLoop/Classes/YtDlpService.cs)), so what really limits a captured Hypnotube session is how long the server keeps it, and nobody has measured that yet.

That makes expiry the criterion that separates the routes. **With a stored password, EdgeLoop can notice a signed-out page and sign in again without bothering the user**, which is exactly what `IwaraApi` already does when its token "ExpiresSoon" ([IwaraApi.cs](../EdgeLoop/Classes/IwaraApi.cs)). Pasted cookies and a WebView2 window both leave the user to sign in again whenever Hypnotube's session runs out, likely every three days or sooner. Firefox import falls in between: the session renews whenever the user browses Hypnotube in Firefox and EdgeLoop reads it again, but a user who only watches through EdgeLoop hits the same expiry. Rule34Video is kinder to every route, because a captured `kt_member` cookie probably lasts longer than the session. Its actual lifetime is unknown.

Plain login has the opposite weakness: it copes with expiry but not with changes to the sites' defences. Both sites already have captcha code. Hypnotube shows a maths captcha on sign-up and password reset, and the KVS client code can show an image code or reCAPTCHA on any AJAX form whose reply asks for one ([Hypnotube signup](https://hypnotube.com/signup); [kvs.min.js](https://rule34video.com/static/js/kvs.min.js?v=3dbf75d2e5)). DDoS-Guard can also switch to a JavaScript challenge that no `HttpClient` can pass. OWASP's guidance against credential stuffing tells sites to add exactly these defences: captchas triggered by risky-looking logins, required JavaScript, multi-step logins with CSRF tokens, and connection fingerprinting ([OWASP Credential Stuffing Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Credential_Stuffing_Prevention_Cheat_Sheet.html)).

The wider downloader world shows what happens on big sites. yt-dlp removed broken password logins for Twitter, Facebook and iQiyi in January 2026, and for Reddit and LinkedIn in July 2026 ([yt-dlp Changelog](https://raw.githubusercontent.com/yt-dlp/yt-dlp/master/Changelog.md)). Reddit's login was removed because Google's captcha became mandatory ([yt-dlp PR #17038](https://github.com/yt-dlp/yt-dlp/pull/17038)). X flagged yt-dlp's login as suspicious and blocked the account for about a day ([yt-dlp issue #12616](https://github.com/yt-dlp/yt-dlp/issues/12616)). Small PHP sites without those defences are where password logins tend to keep working. Even so, EdgeLoop must limit how often it signs in again, so it doesn't repeat the pattern of frequent automated logins that tripped X.

| Criterion | Plain login | Copy-paste cookie | WebView2 sign-in window | Read cookies from Firefox |
|---|---|---|---|---|
| Ease for a non-technical user | Best: type username and password once | Worst: DevTools or an extension, again every time the session ends | Very good: the site's own page in a window | No steps when it works, but only for Firefox users already signed in there |
| Captchas, CSRF, bot protection | None today. Stops working without warning if a captcha or JS challenge is added. Must scrape Rule34Video's CSRF token | Not affected: the user gets past everything in a real browser | The user solves captchas. Requests sent later from `HttpClient` can still hit a challenge | Not affected at sign-in. Same caveat for later requests |
| Session expiry | EdgeLoop signs in again by itself | The user pastes again | The user signs in again | Renews when the user browses the site in Firefox |
| Security and privacy | Holds a reusable password, the most power over the account | One site's session, if the export is limited to that site. Risk from cookie extensions | No password stored. A second copy of the session and browsing history on disk | Reads the browser's cookie store, which is how infostealers work |
| Maintenance | Two login routines that break when a page layout or defence changes | A format parser. Stable | A new dependency, a runtime that updates every two weeks, threading rules | A small SQLite reader, at risk from Firefox's work on encrypting its storage |
| Windows 10/11 | No dependency | No dependency | Built into Windows 11, present on most Windows 10 PCs, updated until at least October 2028 | Doesn't depend on Windows version. Doesn't help Chrome or Edge users |
| Fit with EdgeLoop | Same pattern as `IwaraApi` plus `CookieProtector` | Already built, but reads only header text | Cookies it captures go straight into `CookieProtector`. Needs a new window and package | yt-dlp already gets `--cookies-from-browser`. EdgeLoop's own page requests need their own reader |

The ease ranking comes from the documented steps of each route. No usability study compares them. Across the rows, plain login wins on the two criteria that matter most from day to day, ease and expiry. It loses on security and on resilience to future defences. The other three routes are less alternatives to it than answers to the ways it fails, and the build order below uses them that way.

## The other three routes each cover one of plain login's gaps

### Cookie paste is the fallback that always works, but today's parser is too strict

EdgeLoop's paste box currently accepts only a raw cookie header value, with or without a leading `Cookie:`. It trims the text and warns if `PHPSESSID=` is missing ([SettingsViewModel.cs](../EdgeLoop/ViewModels/SettingsViewModel.cs)). That forces users down the hardest path: find the Cookie header among about fifteen request headers and copy its value. In Firefox, an easier route needs nothing installed. The user opens the Network tab (Ctrl+Shift+E), reloads, right-clicks the first request and chooses "Copy as cURL" (either the Windows or the POSIX version) or "Copy Request Headers" ([Firefox Network Monitor docs](https://firefox-source-docs.mozilla.org/devtools-user/network_monitor/request_list/index.html)). Firefox always writes cookies as `-H 'Cookie: …'`, while Chrome and Edge use `-b`, and the Windows `cmd` versions escape characters with `^` ([Firefox curl.js](https://raw.githubusercontent.com/mozilla-firefox/firefox/main/devtools/client/shared/curl.js); [Chromium NetworkLogView.ts](https://raw.githubusercontent.com/ChromeDevTools/devtools-frontend/main/front_end/panels/network/NetworkLogView.ts)). A copied request includes HttpOnly cookies, because it copies the headers the browser actually sent.

Cookie-export extensions take fewer clicks but come with trust risks. Three open-source ones are reasonable: "Get cookies.txt LOCALLY", "cookies.txt" for Firefox (the one yt-dlp's FAQ recommends) and Cookie-Editor. All three read HttpOnly cookies through the browser's cookies API ([AMO: cookies.txt](https://addons.mozilla.org/api/v5/addons/addon/cookies-txt/); [yt-dlp FAQ](https://github.com/yt-dlp/yt-dlp/wiki/FAQ)). Cookie-Editor alone writes HttpOnly cookies with a `#HttpOnly_` prefix. A naive parser that skips every line starting with `#` would therefore silently drop `PHPSESSID`, but only for Cookie-Editor users ([Cookie-Editor netscapeFormat.js](https://raw.githubusercontent.com/Moustachauve/cookie-editor/master/interface/lib/netscapeFormat.js)). Recommending extensions has a real history of going wrong. In 2023 the original "Get cookies.txt" had a "Featured" badge when an update began sending users' cookies to an outside server, and Google pulled it by 8 March ([Mado no Mori, Impress Watch](https://forest.watch.impress.co.jp/docs/news/1482079.html)). A malicious copycat, "EditThisCookie®", stayed listed in early 2025 ([Cyber Security News](https://cybersecuritynews.com/malicious-editthiscookie-chrome-extension/amp/)).

The fix is in EdgeLoop's parser, not in the instructions. The formats look different enough to detect automatically, so the parser should accept every common one: extension JSON, cURL commands in both escaping styles, Chromium's PowerShell copy, Netscape cookies.txt including `#HttpOnly_` lines, a block of raw request headers, a `Cookie:` line or bare header value, and a bare session token on its own. It should then keep only cookies for that site's domain and report what it found, for example "PHPSESSID found for hypnotube.com, 3 kept, 41 from other sites ignored". Paste stays worth having even after plain login ships for three reasons. It's immune to captchas, it needs no upkeep when a site changes its login, and the user can test with it right now. Pasting a signed-in Hypnotube cookie into the existing box shows whether 720p actually appears, and how long the session lasts, before anyone writes a login routine.

### WebView2 answers captchas and is worth building only once one appears

A WebView2 sign-in window shows the site's real login page in Edge's engine. The user solves any captcha, and EdgeLoop reads the cookies afterwards. The cost is modest. It needs one NuGet package, `Microsoft.Web.WebView2` 1.0.4370.26 (21 November 2026), a 9.37 MB download with no dependencies ([NuGet](https://www.nuget.org/packages/Microsoft.Web.WebView2)). The cookie manager runs in C#, not in page script, and each cookie it returns has an `IsHttpOnly` flag ([Learn: CoreWebView2Cookie](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2cookie)). Microsoft never says in so many words that HttpOnly cookies are included, so a short test should confirm it. There is also no event for cookie changes. Sign-in has to be detected from navigation events plus a test request.

On Windows 11 the runtime is part of the OS. Microsoft says "the vast majority" of Windows 10 PCs have it and advises apps to check for it and link to the download page ([Learn: WebView2 distribution](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)). It keeps getting updates on Windows 10 22H2 until at least October 2028 ([Learn: Microsoft Edge lifecycle](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-support-lifecycle)). Its browser data folder brings its own privacy cost. By default the folder sits next to the executable, which fails with "Access Denied" under Program Files. It stores cookies, history, autofill data and saved passwords, and .NET apps never delete it ([Learn: User data folder](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/user-data-folder)). EdgeLoop would need to put the folder under `%LOCALAPPDATA%\EdgeLoop\WebView2`, turn off password saving and autofill, and offer a "Sign out and forget" button that clears it, or an adult-site browsing history would quietly accumulate outside EdgeLoop's encrypted store.

Two caveats limit what WebView2 buys. First, it only helps with captchas if EdgeLoop leaves the browser as it is. Overriding the User-Agent can drop the client-hint headers ([Learn: CoreWebView2Settings.UserAgent](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2settings.useragent)), and Cloudflare-style clearance cookies are "tied to the specific visitor and device" ([Cloudflare: pre-clearance](https://developers.cloudflare.com/turnstile/get-started/pre-clearance/)). So EdgeLoop's own `HttpClient` could still be challenged after a successful sign-in. Rule34Video's DDoS-Guard is passive today, so this risk is latent, not current. Second, WebView2 does nothing about Hypnotube's three-day expiry. Plain login already handles the current situation, so WebView2 is best held back as the fallback for the day a captcha appears. The login code should detect that day itself: an `errors[]` entry for the `code` field in Rule34Video's JSON, or a `captcha.php` image in Hypnotube's reply.

### Firefox import is a zero-click bonus for this user, not a general solution

Firefox is the only mainstream Windows browser whose cookies an ordinary program can still read in November 2026. `cookies.sqlite` stores values in plain text. When someone reported in 2025 that a non-admin user could export every Firefox cookie silently with yt-dlp, Mozilla called it a "well known issue" ([Bugzilla 1964105](https://bugzilla.mozilla.org/show_bug.cgi?id=1964105)). Firefox locks the file while it runs, and has declined to change that ([Bugzilla 499099](https://bugzilla.mozilla.org/show_bug.cgi?id=499099)). yt-dlp gets around the lock by copying only the main file, and it picks whichever profile's file was modified most recently ([yt-dlp cookies.py](https://raw.githubusercontent.com/yt-dlp/yt-dlp/master/yt_dlp/cookies.py)). That means it can miss a sign-in made seconds earlier that is still in the `-wal` file, and it can pick the wrong profile. EdgeLoop already passes `--cookies-from-browser` to yt-dlp for sites that use it ([YtDlpService.cs](../EdgeLoop/Classes/YtDlpService.cs)). For its own page requests, a small reader would serve better. It would copy `cookies.sqlite` together with its `-wal` and `-shm` files and read only the two sites' rows, so no export of every site's cookies ever reaches the disk.

The route doesn't generalise. Chrome has encrypted its cookies with a key bound to Chrome itself since version 127 in July 2024 ([Google Security Blog](https://security.googleblog.com/2024/07/improving-security-of-chrome-cookies-on.html?m=1)). yt-dlp's issue about the resulting failure on Windows is still open and was locked in January 2026 ([yt-dlp issue #10927](https://github.com/yt-dlp/yt-dlp/issues/10927)). Edge turns the same protection on by default ([Learn: ApplicationBoundEncryptionEnabled](https://learn.microsoft.com/en-us/deployedge/microsoft-edge-browser-policies/applicationboundencryptionenabled)). Every remaining way into Chromium cookies is a technique malware uses.

Even with Firefox, a non-browser program opening `cookies.sqlite` is exactly what the public Sigma detection rule for browser credential theft looks for. That rule exempts programs installed under Program Files ([detection.fyi / SigmaHQ](https://detection.fyi/sigmahq/sigma/windows/file/file_access/file_access_win_susp_process_access_browser_cred_files/)), so a per-user EdgeLoop install would match it. Firefox's reader also has a deadline it doesn't control. Mozilla added automatic SQLite encryption behind a preference in the Firefox 153/154 cycle, though it isn't confirmed to cover cookies ([Bugzilla 1996558](https://bugzilla.mozilla.org/show_bug.cgi?id=1996558)). So this fits as an "Import my sign-in from Firefox" button that is off by default. It should name the profile, read only two hosts, store the result through `CookieProtector`, and when the file can't be read, send the user to the other routes.

## The stored password is the biggest risk, and Iwara's already leaks

Giving an app your password is the pattern OAuth was designed to replace. RFC 6749 lists the problems: the app has to store the password for reuse, it gains overly broad access to the account, the user can't revoke that one app's access without changing the password, and **a compromise of the app exposes the password itself** ([RFC 6749 §1](https://datatracker.ietf.org/doc/html/rfc6749#section-1)). Some users will reuse their Hypnotube or Rule34Video password elsewhere, so that last point matters most. Microsoft's current guidance ranks the options as removing passwords first, then Windows Credential Manager, then DPAPI ([Learn: Handling Passwords](https://learn.microsoft.com/en-us/windows/win32/secbp/handling-passwords)). DPAPI with CurrentUser scope, which EdgeLoop uses, and Credential Manager protect equally against a copied settings file or another Windows account. Neither stops malware running as the same user ([Learn: CryptProtectData](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptprotectdata)). Credential Manager mainly adds visibility: the user can see the entry and delete it.

The concrete weakness is in EdgeLoop's own code. `CookieProtector.Protect` passes no entropy, and if encryption throws it falls back to saving plain text "so the app still works" ([CookieProtector.cs](../EdgeLoop/Classes/CookieProtector.cs)). That's tolerable for a cookie that expires in days. For a password it should refuse to save and tell the user instead. The two new site passwords should never be passed to yt-dlp at all, which it can't use for these sites anyway.

The Iwara path already breaks that rule. `AddSiteArgs` adds `--username <email>` and `--password <password>` to yt-dlp's arguments whenever an Iwara account is set ([YtDlpService.cs](../EdgeLoop/Classes/YtDlpService.cs), lines 475-481). The password then sits in plain text on yt-dlp.exe's command line for as long as it runs. Microsoft warns that command lines "can contain sensitive or private information such as passwords". With process command-line auditing turned on, every command line is written in plain text to the Security event log as event 4688, where anyone who can read security events can see it. The setting is off by default ([Learn: Command line process auditing](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/component-updates/command-line-process-auditing)). WMI's `Win32_Process.CommandLine` exposes the same text to other tools while yt-dlp runs ([Learn: Win32_Process](https://learn.microsoft.com/windows/win32/cimwin32prov/win32-process)), and CWE-214 classifies this as a weakness ([CWE-214 summary](https://mondoo.com/vulnerability-intelligence/cwe/CWE-214)). EdgeLoop's own logger doesn't record the argument list, so the leak is limited to the process listing and the audit log.

The best fix is to **stop giving yt-dlp the password at all**. EdgeLoop already signs in to Iwara through `IwaraApi` and holds its tokens, so if yt-dlp's Iwara path is still needed, it should receive a session rather than the password; whether yt-dlp's Iwara extractor accepts a token or cookie has not been checked. If the password must go to yt-dlp, the next best is a temporary netrc file in a folder only the user can read, passed with `--netrc --netrc-location <path>` and deleted afterwards. yt-dlp's README presents netrc as the way to keep passwords out of command lines, at the cost of a short-lived plain-text file ([yt-dlp README](https://raw.githubusercontent.com/yt-dlp/yt-dlp/master/README.md)), and the 2026.02.21 release fixed a security flaw in the related `--netrc-cmd` option (CVE-2026-26331) and limited netrc machine names to safe characters ([yt-dlp Changelog](https://raw.githubusercontent.com/yt-dlp/yt-dlp/master/Changelog.md)). Piping the password into yt-dlp's interactive prompt is not a real option: Python's password prompt on Windows reads from the console rather than redirected input, though this was not tested.

## Build order, and the tests only a real account can settle

The order below puts the live exposure first and cheap measurements next. Code that depends on the unknowns comes after.

| Step | Work | Why at this point |
|---|---|---|
| 1 | Take the Iwara password off yt-dlp's command line (token, or a temporary netrc). Make `CookieProtector` refuse to fall back to plain text for passwords | A live exposure with a small fix |
| 2 | The user pastes a signed-in Hypnotube cookie into the existing box and measures the result | Proves 720p appears and shows how long sessions last before any login code is written |
| 3 | Add a per-site "still signed in?" check: `js_user_status` for Rule34Video, `/logout"` for Hypnotube. Show "Signed in" or "Session expired" in Settings | Every route uses it. It triggers silent re-login and the fallback prompts |
| 4 | Widen the paste parser to every format, filter by domain and show a summary | It's the fallback every other route relies on, and it needs no upkeep when sites change |
| 5 | Plain login for Hypnotube, then Rule34Video. Store the password with DPAPI, sign in again at most once per launch or when a request fails (with backoff), and send the user to the paste route when a captcha is detected | The biggest win: 720p with no recurring chore |
| 6 | An optional "Import from Firefox" button with its own two-host reader | No clicks for this user, and a cheap addition |
| 7 | A WebView2 sign-in window, built only when a login captcha or JS challenge appears | Insurance. Puts off adding the dependency until it's needed |

This research didn't submit any credentials. Every success path is inferred from page source and other tools' code, so the user needs to confirm the following with their own account.

| What to verify | When | Why it changes the plan |
|---|---|---|
| A signed-in Hypnotube session gives 720p both in EdgeLoop's own requests and through yt-dlp's cookie file | Before step 5 | It's the whole payoff. If 720p doesn't appear, the login work is wasted |
| How long a pasted Hypnotube session really lasts: after 30 minutes idle, one day and three days. Also whether the site refreshes `Max-Age` on later requests | Before step 5 | Decides how much silent re-login matters compared with paste |
| Whether sessions are tied to the IP address or User-Agent (switch the VPN on and off), and whether Hypnotube's location gate blocks signed-in pages | Before step 5 | A VPN switch could invalidate every captured session. No route gets around the location gate |
| What Hypnotube's login reply contains: the redirect, whether `PHPSESSID` changes, any new cookies, and whether `/logout"` appears | During step 5 | Defines the success check and which cookies to keep |
| On Rule34Video: the shape of the JSON success reply, whether the CSRF token is enforced, `kt_member`'s expiry, whether the session is rebuilt from `kt_member` alone, and whether `js_user_status` returns an id above 0 | During step 5 | Decides whether a pasted or captured cookie set lasts long enough |
| What one deliberately wrong password returns, tried only once | During step 5 | Lets EdgeLoop tell a failed login from a captcha without risking a lockout |
| Whether DDoS-Guard accepts .NET `HttpClient`, whose TLS fingerprint differs from curl's | During step 5 | A challenge here would bring WebView2 forward |
| Whether yt-dlp's Iwara path is still needed and can take a token | During step 1 | Decides between removing the password and using netrc |
| Whether WebView2's `GetCookiesAsync` returns HttpOnly `PHPSESSID`, and whether Firefox import sees a sign-in made seconds earlier when the `-wal` file is copied too | Steps 6-7 | Not documented anywhere. A ten-minute test settles each one |

## Conclusion

The choice turned on one site's cookie, not on the general case for passwords or cookies. If Hypnotube's sessions turn out to last weeks, pasting cookies or using a WebView2 window would be good enough and EdgeLoop could avoid storing passwords altogether. That is why the cheapest experiment in the plan comes so early: pasting one cookie into a box that already exists. It answers the two questions that would most change the recommendation, whether 720p appears and how long a session lasts. The routes also share one primitive, the per-site "am I still signed in?" check. Built first, it makes every route interchangeable and turns plain login's worst failure into something visible. Without it, a dead login looks like "no 720p today", not like an error.

Browsers are also making it steadily harder to lift cookies out of them. Chrome and Edge already bind cookie encryption to themselves, Firefox has built SQLite encryption behind a switch, and Chrome is rolling out device-bound sessions on Windows ([Chrome for Developers: DBSC on Windows](https://developer.chrome.com/blog/dbsc-windows-announcement)). Routes where the site issues the session straight to EdgeLoop, plain login now and WebView2 later, don't depend on any browser's internals. That makes them the more durable foundation, as long as EdgeLoop treats the password it holds as the most sensitive thing it stores. Its handling of the Iwara password shows it doesn't do that yet.
